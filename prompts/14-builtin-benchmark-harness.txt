Корректность измерения. Прогрев до стабилизации; число итераций адаптивное под бюджет времени, но фиксируемое и записываемое в отчёт для воспроизводимости; результат функции сохраняется в sink, чтобы V8 не вырезал работу; проверки результата (verified) выполняются вне замеряемого участка, и кейс, давший неверный результат, помечается failure, а не быстрым. Разделяй стадии, как в zaxis разделены CPU layout/encode/GPU: время компиляции не смешивается со временем исполнения, а время загрузки модулей не входит в замер горячей функции. Запускай каждый сценарий в изолированном процессе или worker для чистого JIT-состояния, режим по умолчанию изоляция, --in-process для быстрой отладки. Фиксируй окружение: версия Node, V8, ОС, CPU модель и число ядер, git commit и состояние dirty, режим dev/release, версия Slim. Один шумный прогон ничего не доказывает: сравнение допустимо только при равных кейсах, размерах, числе выборок и окружении, иначе compare отказывается и объясняет почему.

CLI: npm run bench [-- флаги] и slmc bench-self не нужен; достаточно npm run bench. Флаги: --quick (мало выборок, малые размеры, секунды), --hard (много выборок, большие размеры), --suite compiler|runtime|examples, --filter text,text, --list, --sizes N,N, --iterations N, --warmup N, --release, --isolate/--in-process, --output PATH (по умолчанию target/bench/benchmark.json), --max-p95-ms N и --max-regression PERCENT для бюджета, --save NAME и --compare NAME|PATH. Вывод: таблица кейсов с p50/p95/p99, разбросом и пометкой шумного результата, затем сводка failure/unsupported. Код выхода ненулевой при failure, превышении бюджета или регрессии выше порога. Отчёт JSON содержит поля completed, failure, verified, unsupported, как в zaxis, и проверка этих полей, а не только наличия файла, описана в документации.

CI-режим: сценарий, который запускается на pull request с фиксированным набором --quick кейсов, публикует таблицу различий в виде Markdown (--format markdown) и не падает на шуме ниже порога; выложи пример workflow-файла в docs или комментарием, не активируя его без согласования. Базисы хранятся в bench/baselines/ как JSON без машинно-зависимых абсолютных путей и с пометкой окружения.

Тесты самого харнесса (в обычном npm test, быстрые): статистика на известных выборках (перцентили, MAD, отсев), разбор опций и ошибки на плохих значениях, compare на искусственных базисах (регрессия, улучшение, несовместимое окружение), JSON-схема отчёта, что провальный кейс даёт failure, что --list не запускает измерений, что кейс с неверным результатом не считается успешным. Сами замеры тестами не проверяй.
